# MediAgent

An in-progress, doctor-supervised healthcare workspace. Use synthetic data only: this build has not undergone clinical, security, privacy, or legal assessment. The API and database-backed background services accept only `APP_ENV=development` (the default); all other values fail startup, including production and misspellings.

MediAgent explores document extraction, retrieval-augmented generation, and consent-scoped tools for healthcare workflows. Contributions are welcome: see [CONTRIBUTING.md](CONTRIBUTING.md), the [roadmap](docs/ROADMAP.md), and the [MIT License](LICENSE).

Authentication rate-limit keys use keyed digests of identities and addresses. API instances sharing Redis must use the same `JWT_SECRET`; changing it resets their active authentication rate-limit windows. The local default is public and provides no protection against guessing key contents.

The API marks HTTP responses `Cache-Control: no-store`, including errors, to reduce the risk of caching patient data. Deployment proxies and clients must also respect that policy.

DOCX parsing preserves simple, unmerged table rows using inserted pipe separators, allowing recognized lab and medication columns to be transcribed with text-segment evidence. Complex or merged tables fall back to flattened text and must be checked against the original; DOCX segments are not page numbers. Some converters flatten tables into ordinary paragraphs before saving; their original rows cannot be reconstructed reliably and are not automatically extracted as tables.

DOCX segments break only between lines to avoid recording a partial line as a complete field. Lines longer than 30,000 characters or documents that cannot fit in 30 segments fail processing and require manual review.

## Implemented so far

- Patient and doctor registration, scrypt password hashing, short-lived JWTs, hashed rotating refresh tokens, session revocation on logout, and password-confirmed account deactivation. The browser stores tokens in HttpOnly, SameSite cookies through a same-origin Next.js proxy.
- Out-of-band administrator creation; doctor accounts begin unverified. An administrator can change verification state without being granted patient-record access.
- Patients and doctors can maintain self-reported profiles. Viewing a patient's profile requires a separate, time-limited profile consent. Changing a verified doctor's profile returns their verification to pending. Organization affiliation is free text, not verified membership or a tenancy boundary.
- Patients can create a relationship with a verified doctor, grant time-limited document access, inspect consent history, and withdraw a grant. A relationship can be ended through the API. Each patient-record read checks the current state.
- Patients can separately grant clinical-note access. A verified doctor can create a draft, submit it, approve or reject it with a reason, compare versions, and create amendments; patients see approved versions only. An approved version remains visible while its amendment is pending, and previous versions remain in the clinician's history.
- Patients can separately grant consultation access. Verified doctors can record completed consultations and associate a new clinical note with one of the patient's consultations; the association stays fixed across note versions.
- Patients and their verified doctors can exchange relationship-scoped messages when messaging consent is active. Messages are separate from AI conversations and are not an emergency service.
- The doctor worklist shows patients with an active relationship and at least one active consent, plus recent uploads and pending note and transcription reviews according to their separate scopes.
- In-app notifications record care relationship creation, consent changes, note review requests, and document processing outcomes. Notification records are created transactionally with the underlying event and have per-recipient idempotency keys.
- Private local document storage for PDF, DOCX, JPEG, and PNG, with basic extension, MIME, signature, filename, and byte-limit checks. Authorized users can list and download documents; uploaded documents are marked unverified.
- Uploads automatically queue asynchronous text extraction; patients can request reprocessing. A Redis/Celery worker uses PyMuPDF for native PDF text, local Tesseract OCR for pages without native text and for PNG/JPEG images, and bounded WordprocessingML text extraction for DOCX. Results are explicitly unverified and retain page or logical-segment attribution; results use the document's existing access policy.
- Patients and authorized doctors can view an overview of transcribed laboratory and prescription items. It uses the latest completed current job and latest transcription version in pages of up to 25 documents, links back to the original, and labels clinician-reviewed and unverified values. It is not a confirmed medication list or interpretation; a new pending or failed processing job temporarily removes that document from the overview.
- The review workspace displays a page-by-page raster preview beside extracted fields and text. Clicking evidence opens its source page; each preview request checks document access before and after rendering. Previews use a bounded in-memory snapshot and validate the upload digest when one exists, so rendering does not reopen a changed original path.
- A conservative, versioned transcription parser recognizes explicit labels, supported pipe tables, and certain aligned native PDF laboratory tables; it links each captured value to the extracted page text. An authorized verified doctor with both document-view and document-review consent can correct and review a transcription; earlier versions remain available.
- Administrators can enter reference text or stage a separate PDF/DOCX reference import, provide provenance and version metadata, index it using a configured embedding provider, approve it, and retire it. Search uses pgvector and returns only approved, currently effective, indexed source chunks with provenance. Patient uploads are not automatically ingested into this collection.
- Private, patient-scoped assistant conversations persist messages and stream checked responses over WebSockets. A verified doctor needs assistant consent, plus document or note consent for each selected context type. One-use tickets authenticate the socket and access is rechecked for turns and streamed chunks. A configured Ollama chat model is optional; generated text is labeled unreviewed.
- Users may explicitly save, inspect, change, or delete a fixed assistant response-length preference. It is stored per account outside patient records and is not clinical history.
- An authorized doctor can write an unapproved note using an evidence-cited assistant response as a reference. The note retains a source link across amendments; opening the private response requires its original conversation permissions.
- A local stdio MCP adapter exposes authorized document listing and extraction, self-reported patient profile, consultation history, and approved knowledge search through scoped, individually revocable credentials. Every integration call is rate-limited and rechecks the owner's access and patient consent.
- Administrators can inspect bounded audit metadata and aggregate document-job status. The operational view excludes document contents, filenames, prompts, messages, and user-entered audit purpose text.
- Administrators can search account identity and status and deactivate patient or doctor accounts with an audited reason; this does not grant them access to patient records.
- PostgreSQL-backed async SQLAlchemy models and Alembic migration for users, sessions, relationships, consent, documents, and audit events. The frontend connects to these APIs.

By default uploads are not malware-scanned, and signature checks do not establish that a file is safe. An optional ClamAV integration can reject detected files and scanner failures before accepting them. Uploads are streamed through the local proxy and bounded before and during multipart parsing; an externally deployed reverse proxy still needs its own body, time and connection limits. Parser subprocesses receive only the OCR configuration and, when requested, the vision configuration; they do not inherit database or signing secrets in their environment. Linux parser processes have individual memory and CPU limits, and worker output and runtime are bounded. Preview subprocesses also receive a restricted environment. These measures are not a hardened sandbox: the parser shares the container identity and filesystem and can access the worker network. The worker container has resource limits and read-only upload mounts, but retains database and broker access. The bundled OCR language data supports English; OCR can misread or omit text, and the default PDF mode may miss scanned content on a page that also has native text. The structured parser recognizes a small set of explicit labels, limited pipe-delimited tables, and native PDF lab tables with specific aligned column headings; it does not generally understand arbitrary tables or complex layouts and is not clinically validated. Native table geometry can misassociate fields; text evidence alone does not prove row alignment. It does not attach fields across page or DOCX-segment boundaries; orphaned or ambiguous fields are omitted with a review warning, so continuation values may require manual entry. Warnings are capped at 100; the final warning indicates when additional warnings were omitted. OCR evidence refers to recognized text, not verified original image content. A transcription review does not approve a clinical note or verify the original report. Knowledge ingestion does not authenticate sources; assigned clinician review is optional by default and requires independent governance. Consent grants and relationship creation/restoration share a limit of 60 per user and 600 per peer address per minute; document uploads and processing requests each have a limit of 20 per user and 200 per peer address per minute. The limits use Redis, fail closed if unavailable, and record bounded audit metadata; withdrawal and relationship termination are not subject to these new limits. The local proxy shares a peer address across users. Some other sensitive operations still need rate limits. Email ownership verification defaults to the local mail catcher and does not gate sign-in; an account reactivation procedure is not implemented. The default development policy permits doctor self-review; set NOTE_REVIEW_POLICY=independent to require another authorized doctor. See [the roadmap](docs/ROADMAP.md).

## Run locally

Requirements: Git and Docker with Compose. Clone the repository and start the local stack:

```bash
git clone https://github.com/Imyashmathur/MediAgent.git
cd MediAgent
cp .env.example .env
# Set a unique JWT_SECRET in .env before starting the stack.
docker compose up --build
```

For a local secret, generate a random value with `openssl rand -hex 32` and set `JWT_SECRET` in `.env`. Never commit `.env`.

Open http://localhost:3100; API documentation is at http://localhost:8100/docs. The core workspace runs without an AI model; assistant responses, AI document summaries, and knowledge indexing require additional configuration. Compose starts the migration before the API. Create a local administrator in a second terminal:

```bash
docker compose exec api python -m app.create_admin
```

Follow the interactive prompts, then sign in as that administrator and verify a registered doctor by ID. The doctor can share their displayed ID with a patient, who can create a relationship and grant access. A doctor can then open that patient's document list using the patient's ID. Local Compose uses HTTP and intentionally disables the cookie `Secure` flag; never expose this configuration to the internet.

### Configure local AI features

Ollama and models are optional for the core workspace. To try the assistant,
AI summaries, and knowledge indexing on Docker Desktop:

1. Install and start [Ollama](https://ollama.com/). Pull a chat model and the
   default embedding model on the host:

   ```bash
   ollama pull qwen3:4b-instruct
   ollama pull all-minilm
   ```

2. In `.env`, set the following values. `host.docker.internal` is the Docker
   Desktop address for an Ollama service running on the host; other Docker
   environments need a host address that containers can reach.

   ```dotenv
   OLLAMA_BASE_URL=http://host.docker.internal:11434
   OLLAMA_CHAT_MODEL=qwen3:4b-instruct
   OLLAMA_EMBED_MODEL=all-minilm
   ```

3. Recreate the services so they read the updated configuration:

   ```bash
   docker compose up -d --build
   ```

The embedding model must return 384-dimensional vectors. To use retrieval,
add reference material as an administrator, index it, and approve it; patient
uploads are not automatically added to the reference collection. Chat and
summaries send selected extracted text to the configured Ollama service.

JPEG and PNG uploads automatically request vision transcription and require a
configured vision-capable model; see [vision setup](docs/VISION_DESIGN.md).
PDF vision transcription is optional. Model output, OCR, and comparisons are
unverified; use synthetic data and check the original with a clinician.

To create a complete opt-in synthetic workspace, start the stack and run:

```bash
docker compose exec api python -m app.seed_synthetic
```

Supply an existing local administrator’s credentials at the prompt. The script creates randomly named synthetic patient and doctor accounts, verifies the doctor through the administrator API, grants four permissions for 24 hours, processes a synthetic PDF, and approves a synthetic note using the local self-review policy. Generated passwords are shown once in the terminal; store them securely if needed. This writes persistent synthetic users and records to the local database. If it fails or is interrupted, partial records may remain. Use the dashboard to withdraw permissions or deactivate the synthetic accounts. Do not run it against real patient environments. The worker and dispatcher must be running; no external model or paid service is required.

For backend tests without Docker, use Python 3.12, install `backend/requirements.txt`, and run `python -m pytest` from `backend/`. To run migrations against SQLite locally, run `alembic upgrade head` in `backend/`. PostgreSQL is used in Compose. The default backend suite skips tests that require services; with Compose running, enable PostgreSQL and Redis integration tests using `docker compose exec -T -e MEDIAGENT_POSTGRES_TEST=1 api python -m pytest tests/test_postgres_notes.py -q` and `docker compose exec -T -e MEDIAGENT_REDIS_TEST=1 api python -m pytest tests/test_auth_rate_limit.py -q`. The Compose smoke test can be run from the repository root with `MEDIAGENT_COMPOSE_SMOKE=1 backend/.venv/bin/python -m pytest backend/tests/test_compose_smoke.py -q`; it creates synthetic records and checks native PDF and image OCR processing, unverified structured values and page evidence, cross-patient denial, and a WebSocket turn. Local Ollama tests require separately configured models. Frontend build: `npm ci && npm run build` in `frontend/`.

With the local Compose stack running, use Node 22.22.2 or later in the Node 22 line, Node 24.15 or later in the Node 24 line, or Node 26 or later. From `frontend/`:

```bash
npm ci
npm test
npx playwright install chromium
npm run test:e2e
MEDIAGENT_E2E_ADMIN_SEED=1 npm run test:e2e
```

The default browser suite tests synthetic patient registration, isolation, document processing and deletion, plus automated WCAG A/AA checks on selected screens. The opt-in administrator-seeded test additionally exercises clinician verification, consent, transcription review, note approval and withdrawal using local Docker Compose, including denial of administrator patient-record access and retention of the patient’s approved note. It creates a synthetic administrator with a random password and deactivates it in cleanup; interruption or forced termination can prevent cleanup, so check for and deactivate any leftover synthetic administrator. The tests create synthetic accounts and records in the configured local database; do not run them against real patient data or an external service. To use an installed Chrome instead of Playwright's Chromium, set `PLAYWRIGHT_CHANNEL=chrome`. Screenshots, video and traces are disabled; Playwright can still write failure context under the ignored `frontend/test-results/` directory. Automated checks cover only the screens and rules tested and do not establish accessibility conformance; manual keyboard, screen-reader and inclusive-user testing are still required.

## Architecture

```text
Browser ──> Next.js same-origin proxy ──> FastAPI authorization/services ──> PostgreSQL
               HttpOnly cookies                 │             └──> private local upload volume
                                                └──> Redis ──> Celery worker ──> OCR subprocess
```

The API rechecks account, session, clinician verification, relationship and consent for each patient document read. Audit records share the database transaction with successful state changes and denied access attempts. Refresh tokens are stored as SHA-256 hashes and rotate atomically. Revocation blocks both the access and refresh token for that session. Logout can use the current refresh credential when the short-lived access cookie has expired. The immediately previous refresh hash can revoke the session during a concurrent rotation but cannot refresh or access data; an older credential cannot do so. If the application cannot confirm logout, the UI reports that the server session may still be active. There is no organization or tenant model yet, and no emergency-access bypass.

A dated [India privacy and healthcare source review](docs/INDIA_PRIVACY_REVIEW.md) links official DPDP and ABDM materials and identifies unresolved deployment questions; it is not legal advice or a compliance assessment. Local files lack encryption at rest, mandatory malware scanning, automated retention schedules, and backup/restore automation. The opt-in S3 adapter is incomplete and intended only for synthetic testing. A [manual synthetic backup and isolated restore runbook](docs/LOCAL_RECOVERY.md) is available for local-only storage; its preflight rejects object-storage references and it is not a production recovery system. Production requires further hardening and independent assessment; no compliance or clinical safety claim is made.

New uploads record a SHA-256 digest while streaming. Before parsing, the worker copies the bounded regular file into a private temporary directory and checks the copy against that digest; this prevents a change to the original after verification from changing what the parser reads. The worker checks the original again after parsing and rejects the result if it no longer matches the snapshot. Knowledge imports use the same snapshot mechanism with their stored hash. Downloads read a bounded in-memory snapshot and verify its digest before rechecking access and returning it. Existing documents remain usable but have no trusted digest until replaced; their downloads and previews check size and regular-file metadata but cannot verify content integrity. Temporary files are cleaned up after normal completion or handled failures. The local Compose worker pins its temporary directory to a 128 MiB `tmpfs`; an interrupted process can leave a copy there until the container stops. Tmpfs uses the worker's memory limit and may be written to host swap, so it is not encryption or guaranteed secure erasure. The bound can cause jobs to fail if upload limits are raised without adjusting the worker mount and memory limits. Other execution environments and processes may use disk-backed temporary storage. Download snapshots are bounded by the configured upload limit and four concurrent reads per API process; they use memory and may reject files if the limit is lowered below their size. Downloads return a whole-file response and do not support byte ranges; access changes after response bytes are released cannot recall those bytes. This is not a hardened sandbox and does not protect against a compromised database or worker. Uploads automatically create processing jobs; subsequent reprocessing requires a patient request. Jobs and their dispatch records are committed together. The Compose dispatcher retries Redis publication with bounded backoff, and administrators can inspect dispatch counts through the operations API. Delivery is at least once: a crash after publishing can cause duplicate messages, which the worker claim prevents from processing twice. The dispatcher recovers worker claims older than five minutes, up to three claims; claim tokens prevent an expired worker from committing results after recovery. A patient can also replace a stale running document job. A job waiting for broker delivery remains queued during an outage. Existing queued jobs from the previous five minutes are included when upgrading; older queued jobs need a new request. Run the dispatcher whenever processing is enabled. Upgrade workers and the dispatcher together; older workers cannot honor claim tokens. The dispatcher republishes jobs that remain queued for five minutes after publication, which can produce duplicates when a queue is slow. The local Redis service does not persist its queue; this retry reduces the impact of lost messages but is not a substitute for durable production infrastructure. Text is stored as patient data; no raw text is intentionally logged. A parser has a 30-page limit, 20-million-pixel image limit, a 180-second job timeout, and a 45-second OCR timeout per page.

Document processing also records an unverified type hint when an extracted line exactly matches a recognized document heading. Conflicting or absent headings produce an unknown type; OCR and layout errors can make hints inaccurate. The hint includes its source location and text layer, is not a diagnosis, and is not used to make access or care decisions. Existing jobs lack a hint until reprocessed.

Patients or doctors can end a care relationship; only the patient can restore it, and only while the doctor is active and verified. Restoration withdraws every old active grant, including scheduled grants, so the patient must grant permissions again. The relationship retains existing messages, which can become accessible again if message permission is regranted. Patients can grant consent immediately or schedule a future effective time before expiry; the server enforces the start time on every protected action, and withdrawal before the start prevents later access. The consent history shows the doctor, effective and withdrawal times, and the grant’s date and relationship state. The list can be refreshed after a relationship changes; client clock differences or a change in doctor account status can affect the display. The server independently checks current consent, relationship, and clinician status for each protected action.

### OCR configuration and mixed PDF pages

Image OCR and preview apply EXIF orientation consistently and flatten transparent pixels onto white; existing jobs must be reprocessed to use this normalization. Incorrect orientation metadata can still produce an incorrect view, and OCR remains unverified. The worker uses the local Tesseract OCR adapter by default (`OCR_PROVIDER=tesseract`, `TESSERACT_LANGS=eng`). The bundled image installs English trained data only. To use other languages, install or mount trusted Tesseract trained data in the worker and set `TESSERACT_LANGS` to installed language codes, such as `eng+hin`; language order can affect results. Configure `TESSDATA_PREFIX` if needed. The adapter checks that all requested languages are installed and fails the job if OCR is disabled, missing, or unavailable; it does not silently substitute another language. `OCR_PROVIDER=disabled` allows DOCX text and native-text PDF pages in fallback mode, but OCR-required input fails; full-page OCR mode requires an enabled provider. See [Tesseract's command-line documentation](https://tesseract-ocr.github.io/tessdoc/Command-Line-Usage.html).

The transcription parser also supports single-line, pipe-delimited laboratory tables with explicit `Test`/`Test name` and `Result`/`Observed value` headers and only recognized optional columns. It also supports prescription tables with explicit `Medicine`/`Medicine name`/`Drug` and `Dose`/`Dosage` headers and recognized optional columns. It keeps exact cell text as page or segment evidence, leaves blank cells unknown, does not infer abnormality or medication instructions, and stops a table after an ambiguous column count. Header and row boundaries must appear in the extracted text on the same page or segment; real PDF tables, OCR errors, merged cells, continuation rows, and other formats may be missed or misread. Table results remain unverified and require comparison with the original. Existing jobs need reprocessing to use this parser.

`PDF_OCR_MODE=fallback` OCRs only pages without native text. Set `PDF_OCR_MODE=all` to also OCR pages with native text; the native and supplemental OCR layers are stored and displayed separately. Supplemental OCR may duplicate or disagree with native text. It is available as a separately labeled assistant and summary source. Explicitly labeled values are transcribed into separate records with layer-specific evidence; these records may duplicate or conflict with native-text records and must be checked against the original. Existing schema 1.0 and 1.1 records remain supported. Mixed-layer transcriptions use schema 1.1 unless laboratory details are present; laboratory details require schema 1.2. Explicitly labeled details and supported native table rows are transcribed with page or text-segment evidence; a clinician can also enter them during review. All OCR is unverified, can omit or misread text, and is not validated interpretation of medical images. The job records the actual Tesseract version and language names when OCR is used; the trained-data files are not hashed, so this is not a complete immutable model identity. OCR on every PDF page can exceed the existing job time limit, particularly for long documents. Config changes require restarting the worker and reprocessing the document.

### Optional vision transcription

Image uploads automatically request vision transcription and require a configured vision-capable Ollama service. For PDFs, a patient can explicitly request additional vision transcription on reprocessing. Page images are sent to the configured service and model; output is a separate unverified layer, not medical-image interpretation and not automatic structured extraction. See [vision setup and limitations](docs/VISION_DESIGN.md). No vision provider is enabled by default.

### Unverified document summaries

A patient or authorized doctor can explicitly generate a summary of the latest completed document extraction. A doctor needs both document-reading and assistant consent. Complete extracted text is split at line boundaries into bounded chunks and sent in batches to the configured Ollama chat model. The system rejects inputs exceeding its limits or containing missing or empty extracted pages instead of silently truncating them. The summary cites source pages or segments and retains the configured model name, but citations identify source sections rather than proving individual claims. Model output is unverified, is not an official clinical record, and can omit or invent information; a clinician must check the original. Requests use durable retry IDs and recheck account, consent, and document state before saving. Model-provider calls can still be repeated after a timeout. Summaries are visible to the patient and clinicians with both permissions, and document deletion removes stored summaries. Data already sent to a provider, copied into notes or conversations, or present in backups cannot be recalled. No clinical safety claim is made.

### Patient document deletion

A patient can request deletion of their own document after entering `DELETE`. The request immediately removes it from document lists, previews, downloads, extraction results, and future assistant context. It cancels active extraction claims and deletes stored extracted pages, structured versions, and document summaries in the same database transaction. A separate `document-purger` process retries removal of the original local file; the patient can inspect pending or completed status, and administrators can see aggregate counts. A minimal tombstone and audit events remain to preserve references and accountability. Run the purger with the API and the same upload volume.

Deletion is not a whole-account erasure or a guarantee of immediate physical destruction. Existing clinical notes, conversations, assistant-generated text, audit records, already downloaded copies, model-provider requests, backups, and filesystem snapshots are retained and can contain information from the document. An already-started operation can have received content before deletion. In-flight assistant responses recheck document availability before saving and streaming, but data already sent to a provider cannot be recalled. No automated backup expiry, secure disk wiping, orphan cleanup, legal retention policy, or external storage deletion is provided. Use synthetic data until these controls and applicable retention rules have been independently reviewed.

### Optional upload malware scanning

The local default `MALWARE_SCAN_MODE=disabled` stores uploads as `not_scanned`; this is for synthetic development data. Set `MALWARE_SCAN_MODE=clamd` and `CLAMD_SOCKET` to an absolute Unix socket path inside the API container to require scanning before either patient-document or administrator reference-file acceptance. Mount a trusted ClamAV daemon socket into that container using a local Compose override. The daemon must be independently installed, kept updated, configured to scan all permitted file types and archive contents, and have `StreamMaxLength` at least `MAX_UPLOAD_BYTES`. See the [ClamAV protocol documentation](https://docs.clamav.net/manual/Usage/ClamdProtocol.html). No TCP scanner connection is supported by this adapter. Scanner timeouts, malformed replies, and connection errors reject uploads with 503; detections are rejected with 422. The database records `not_scanned` or `no_threat_detected`, and existing files are not retroactively scanned. A no-threat result is not a safety guarantee: archive limits, scanner configuration, unknown malware, parser flaws, and files changed after scanning remain risks. Failed uploads are removed from local storage, but a process or host crash can leave an orphaned file; no quarantine, automatic rescan, or scheduled retention workflow exists yet.

## Optional knowledge embeddings

Knowledge indexing and search are disabled until an Ollama service is explicitly configured. Install and run Ollama separately, obtain the `all-minilm` embedding model, and set `OLLAMA_BASE_URL` in `.env` (for Docker Desktop, `http://host.docker.internal:11434` reaches a host service); then restart the API, dispatcher, and worker containers. `OLLAMA_EMBED_MODEL` defaults to `all-minilm`. The model must return 384-dimensional nonzero vectors. The service receives the full reference text and search query, so only configure a provider authorized to receive that data and do not enter patient information into general knowledge search. The dashboard queues indexing for the worker; the administrator can refresh the latest job status and retry a failed job by indexing again. The request is durably recorded in PostgreSQL, dispatch is retried, and expired worker claims are recovered up to three times. Each job rechecks the requesting administrator and session before and after embedding; logging out or deactivation prevents publication. The previous index remains available during reindexing and on failure. A synchronous indexing endpoint remains for compatibility. Before publishing an index, the worker or synchronous API rechecks and locks the administrator account and session, confirms that the source is unchanged and not retired, and rejects a changed model setting. A provider request already sent cannot be recalled. The API records Ollama’s reported model digest when indexing and compares the reported digest before and after embedding. Search includes only indexes with the matching model name and digest; a changed tag requires reindexing. Existing indexes have no digest and must be reindexed before they can be searched or newly approved. This is a best-effort check, not immutable execution: the provider controls the reported digest, and a tag can change between checks or while a model is loaded. Production needs a trusted provider and stronger model pinning and deployment controls. See Ollama’s [list models](https://docs.ollama.com/api/tags) and [embedding](https://docs.ollama.com/api/embed) documentation.

Administrators enter text and provenance, index the draft, and explicitly approve it. Approving a later version retires the previously approved version in the same family; a future version can be approved when it becomes effective. Retirement immediately excludes the source from new searches. Assistant turns recheck all reference excerpts supplied to the model before saving and before streaming; if a source is retired, expires, or changes, the turn is stopped. Existing conversation history and content already sent to a model or streamed before a later retirement are not erased. Historical citations label approval as applying when the response was generated and ask users to verify current status; they do not automatically retrieve current source status. Retrieval returns source excerpts, not medical advice, and uses exact pgvector cosine search. Provider failures return an error rather than invented results. The standard tests mock embeddings; an opt-in integration test also exercises a configured local Ollama model. No clinical validation or model-quality claim is made.

Administrators may upload a PDF or DOCX reference into a separate private knowledge-import volume. A Celery worker verifies the file hash and extracts text, capped at 50,000 characters, without using patient-upload records. The original and import status remain available to administrators. Downloads use a bounded regular-file snapshot, verify the recorded SHA-256 digest, and recheck the administrator session and deletion state before release. An imported draft links to its source file only if its text exactly matches the extracted text; editing the text creates a manually entered draft instead. Import alone does not index or approve a source. Parsing may omit or misread content, so administrators must compare it with the original and independently review provenance. Import dispatch and recovery use the same durable retry mechanism. An administrator can retry a failed import while its original importing administrator remains active; the worker rechecks the staged file hash. Administrators can explicitly delete a staged import: access to its file and extracted text is revoked, active processing is fenced, and the local purger retries file deletion. Import metadata and links from existing knowledge sources are retained; source text already copied into knowledge sources, provider copies, and backups are not deleted. Removal is not secure erasure or an automatic retention policy. This staging area is not an external source-authentication or malware-scanning system.

## Experimental assistant

Set `OLLAMA_BASE_URL` and `OLLAMA_CHAT_MODEL` in `.env` to enable model generation; knowledge retrieval additionally requires an indexed source and the embedding model described above. Questions, recent conversation history, and any explicitly selected documents, notes, consultation metadata, profile fields, or knowledge excerpts are sent to that configured service. Only configure a provider authorized to receive this information. Conversations are private to their creator; a doctor requires separate patient consent for assistant use and for every selected or previously used record scope. A revoked scope blocks future access to that conversation's history as well as new turns. The assistant uses a document’s latest job only when it is completed; it rechecks the selected extraction and includes the job ID in new citations. Reprocessing or changed text during generation stops the turn. When a turn uses approved clinical notes, their exact versions are rechecked before the response is saved and streamed; an amendment approved during generation stops that turn. Already saved history and information sent to a provider or streamed before a later amendment remain available under the existing access rules.

A clinician can link an accessible patient document to a note draft; the note shows a download link that independently checks document access. Draft revisions retain the link, and amendments inherit it when the source field is omitted. API clients may explicitly select another authorized source or send null to remove the link in a new version; prior versions retain their history. The document may be deleted or access later withdrawn, so a link does not guarantee availability or clinical verification.

For a completed, evidence-cited assistant response, its clinician owner may write a separate note draft and link that response as a reference. This requires both clinical-note access and all current permissions needed for the conversation; an emergency response or uncited fallback cannot be used. The doctor must write and verify the content, then use the normal submit and approval process. The reference is retained through amendments, and an approved note discloses that an assistant response was referenced. Opening the original response and citations remains restricted to the conversation owner with current conversation permissions; other clinicians with note consent can see the note but cannot open that private conversation. The note follows clinical-note access rules after creation, independently of later assistant-consent changes. An authorized clinician may also generate an AI-assisted draft from a completed assistant response that cites patient records. This sends the unreviewed response to the configured model again, applies the existing output and safety checks, and saves the result as a draft only after rechecking current session, consent, and source access. The clinician can revise the draft as a new version, then submit it for review. AI assistance and the assistant-source link persist across versions and remain visible after approval. The model sees the assistant response rather than the full original records, and may omit or invent details; the clinician must check the original evidence. No safety check guarantees accurate or safe output. Generation requests require a client-generated UUID. Retrying the same request and inputs returns the original result after rechecking access, while an active request returns a conflict; failed or abandoned requests can be retried with the same UUID. A fresh UUID requests a separate draft. The browser retains an unanswered request ID in session storage for retries. An expired worker claim is fenced from saving a second note, but model calls can still be repeated after a timeout.

Assistant preference memory is opt-in and currently supports only a predefined response style: concise, balanced, or detailed. It is owned by the signed-in account, never copied from a patient's profile or conversation, and may be deleted in the assistant settings. The selected style becomes a fixed instruction on later model calls; it does not bypass safety checks or deterministic routing. Deleting a preference stops using it on future calls but cannot recall a request already sent to a provider or alter previously generated conversation messages. The model may not reliably follow the requested style.

The assistant lists conversations for the selected patient in bounded pages. Each request scans up to 50 owned conversations and checks current permissions before displaying them, so a page can be empty even when older accessible conversations exist; use “Load older conversations” to continue. The cursor is the last scanned owned conversation ID and can identify a conversation whose current permissions prevent listing its details. Assistant conversation history returns the latest 100 messages by default; older pages use a timestamp-and-ID cursor and repeat the current conversation authorization checks. Returning to the latest page or finishing a turn shows new messages. New messages do not shift older pages, and a deleted cursor message invalidates that cursor. Model context still uses only the six most recent stored messages and may omit earlier discussion.

A turn can explicitly include patient-reported profile allergies, medications, and medical history. Each field is capped at 2,000 characters, citations flag truncation, and demographics and contact details are not sent. Blank fields are unknown, not confirmed absences. Doctors require current profile and assistant consent, including on subsequent conversation reads; the selected profile text is checked again before output. These entries are self-reported and can be incomplete or outdated.

Assistant turns can optionally include the five most recent recorded consultation titles, times, and doctor identifiers. Doctors need current consultation consent as well as assistant consent; conversations containing such turns continue to require consultation consent. These records contain metadata, not clinical findings, so a consultation title cannot support a clinical summary. Approved notes are a separately selected source and require clinical-note consent. Users can enter a consultation ID and select both consultation and note context to supply only that consultation and up to three of its linked approved note versions; other notes are excluded. The association and the exact note version are rechecked before output, and note citations identify the consultation. If no approved note is linked, the assistant has only the consultation metadata and cannot derive clinical findings from it. Source records and permissions are rechecked before releasing generated text. This is bounded context, not a complete medical history.

Browser knowledge searches recheck the access token, session, and account after the embedding request before returning results. Approved-reference search is selected by default for non-routed assistant turns; users may turn it off. The question is sent to the configured embedding service for that search, including when patient context is selected. The response explicitly records when the search was unavailable, returned no sources, or returned sources that the answer did not cite. A retrieved citation does not establish relevance or prove a claim. Deterministic emergency and prescription routing runs before reference search.

The assistant routes a limited set of potential emergencies and direct prescription requests deterministically. Its breathing and chest phrase checks are deliberately broad: a match prompts human attention even when the phrase may describe a non-emergency, and unrecognized wording may be missed. See [NHS guidance on shortness of breath](https://www.nhs.uk/symptoms/shortness-of-breath/) and [chest pain](https://www.nhs.uk/symptoms/chest-pain/); these sources do not validate this software. It sends other evidence-based drafts through structured-output validation, source-ID checks, a simple deterministic output filter, and a second model safety check. No such combination guarantees clinical safety or prevents prompt injection, unsupported claims, or missed emergencies. All generated responses remain unreviewed and are not clinical records; qualified clinicians must evaluate them. This is a development prototype, not a medical device or emergency service. The model output is buffered for checks before chunks are sent; cancellation is supported and a disconnected client can reconnect to persisted history. Each authorized assistant turn is limited to 20 per user and 200 per direct peer address per minute across connections; Redis outages block new turns. A rejected turn is not saved and receives general urgent-care guidance. Cancellation remains available, and the bundled proxy shares its peer-address limit across users. The local WebSocket endpoint defaults to port 8100 and allows only the origins listed in `WS_ALLOWED_ORIGINS`; deployment behind a TLS proxy requires additional configuration and review.

# Authentication throttling

Registration, login, refresh, and password reset use atomic Redis counters with one-minute windows. Redis outages cause these endpoints to return 503; logout remains available. The API uses the direct peer address and does not trust forwarded headers. With the bundled web proxy, browser traffic shares the proxy's address limit; a deployment needs an explicitly trusted proxy and appropriate per-client limits before external use. Password hashing runs off the event loop.

Password-reset links expire in 15 minutes and can be used once. Successful reset invalidates all other reset requests, sessions, and integration credentials for the account. By default, Compose sends messages only to Mailpit at http://localhost:8125; the default does not deliver real email. The request ID is queued without an email address or token, and a domain-separated HMAC of that ID is used as the token. The browser clears the URL fragment after opening the reset page. Each reset request and its delivery record are committed together. The reset-mailer retries local SMTP failures up to eight attempts while the token remains valid, and discards requests that have expired, been used, or belong to an inactive account. Requests created before this migration are not backfilled; request a new link if an older one does not arrive. The operations screen shows aggregate delivery states. SMTP acceptance is not proof of delivery; a crash after acceptance but before the database commit can send duplicate messages, despite a stable Message-ID. All copies contain the same single-use token. An explicitly configured SMTP provider can be used for synthetic testing; secret rotation policy, delivery reconciliation, and independently reviewed production configuration are still needed.

An authenticated user can deactivate their account after confirming their password. This disables login and future access, revokes sessions, integration credentials, reset links and unused socket tickets, and records an audit event. A patient's deactivation also denies subsequent patient-record access by their care team. It retains records, relationships and consent history; it is not a deletion request. Operations already in flight may finish, and there is no supported reactivation or data-erasure workflow yet.

Administrators can search paginated account metadata and deactivate patient or doctor accounts for a selected reason. Administrator accounts cannot be deactivated through this management endpoint. The operation uses the same revocation transaction as self-deactivation, and patient deactivation also blocks later clinician access to that patient's records. The search returns names and email addresses, which are sensitive account data, but does not return medical content. Search terms are sent in the request body. There is no administrator reactivation or deletion workflow.

Profile fields are optional and missing fields remain unknown; they are not clinical verification or a substitute for a medical history. Profile updates replace the editable fields as a group. Patient profile access is separate from document and note permissions. Doctors may inspect their own profile and administrators may inspect doctor profiles for verification, but administrative access does not grant access to patient profiles. No actual organization membership model is implemented.

Clinician verification decisions require the profile revision and verification-state revision returned by the review screen. Profile edits and decisions serialize on the clinician account; stale decisions are rejected, and changes to a verified or rejected profile return it to pending. Decisions record the reviewer, status, and profile revision, but historical profile contents and the evidence used for independent credential checks are not stored. Verification still relies on an external human review process and is not a credential-checking service.

Consultations record a title, clinician, and time for a completed encounter; they do not schedule appointments or confirm that an encounter occurred. A patient can view their own history. A clinician needs active consultation consent to create or read consultations and to link a new note. Note access uses separate clinical-note consent; a note retains its consultation identifier as part of its history even if consultation consent is later withdrawn. Existing unlinked notes remain unlinked, and the link cannot be changed through amendments.

Preview renders a page into a non-interactive PNG in a subprocess, bounded to 30 pages, 1,600 pixels per side, 15 seconds, and two simultaneous renders per API process; Linux subprocesses also have memory and CPU limits. It is not a hardened sandbox and does not replace malware scanning. Some interactive PDF elements may not be represented. Authorization is checked before and after rendering; already displayed or downloaded data cannot be recalled when consent changes. The original remains available through the authorized download endpoint until deletion is requested.

DOCX parsing reads bounded main-document WordprocessingML text, including paragraphs within tables, without executing macros or following links. It rejects encrypted entries, macro payloads, unsafe archive paths, excessive archive sizes and XML DTDs. Text is divided into logical segments of at most 30,000 characters, not physical pages; evidence explicitly records `text_segment` as its location type. Headers, footers, footnotes, images, text boxes, layout, and other complex content may be omitted. There is no visual DOCX preview or OCR of embedded images; download the original to inspect it. As with PDF extraction, the parser is not clinically validated or a hardened sandbox.

The upload endpoint authenticates before reading multipart data, allows one file and no other form fields, and limits total streamed request bytes to `MAX_UPLOAD_BYTES` plus 64 KiB of multipart overhead. File bytes are checked separately against `MAX_UPLOAD_BYTES`. Multipart parser temporary files are closed on errors and cancellation. The local Next.js proxy streams uploads to the API and caps other request bodies at 1 MiB; the proxy and API must use the same upload limit. Frameworks or hosting infrastructure outside the bundled local stack may buffer requests, so deployment-level limits and upload timeouts remain necessary.

Care messages are stored per patient–doctor relationship. Both parties can send while the relationship, clinician verification, and separate messaging consent are active; doctors lose read and send access when consent is withdrawn or the relationship ends. Patients retain access to their own message history. Each accepted message also creates a content-free in-app notification for the other participant in the same transaction. Doctors see it only while their relationship and messaging consent remain active; patients retain their own notifications after withdrawal. The notification identifies the relationship, and the recipient must refresh its message thread. The UI shows up to 100 messages per page, can request older pages, and refreshes to the latest messages on request; there are no external alerts, delivery guarantees, attachments, or emergency monitoring. Each page request rechecks access; a cursor whose message has been removed becomes invalid, and newly arrived messages appear after refreshing to the latest page. Existing messages are not backfilled with notifications. Sending uses a Redis-backed limit of 30 messages per user and 200 per peer address per minute; as with other limits, the local web proxy shares its peer address.

The admin operations screen reports database and Redis connectivity, aggregate extraction, knowledge-import, and knowledge-index job states, dispatch counts, and reset-mail states; a job older than five minutes is only flagged as possibly stale, not proven stuck. It does not check worker or model-provider health. Audit review returns up to 100 events per page, newest first, and excludes user-entered purpose and resource details while retaining actor and patient identifiers as sensitive operational metadata. Cursor pagination uses the last event’s timestamp and identifier; newer events added after the first page are not shown until the review is restarted. A removed cursor event invalidates the cursor. HTTP requests receive a server-generated correlation ID returned in `X-Request-ID` on handled responses; audit events created by that request share the ID. Each WebSocket connection has its own ID. Document-processing, knowledge-import, and knowledge-index completion or failure audit events reuse their initiating request correlation ID across worker retries, including exhausted-claim recovery. Jobs created before this change use independent IDs; other background job types are not linked to their originating requests. The local API process keeps bounded counts of response outcomes, duration buckets, and chat/embedding provider failures without request paths or content; unconfigured providers are counted as failures when called. These counters reset on restart, are not aggregated across processes, and are not a substitute for a monitoring system. The bundled API disables Uvicorn access logs; other infrastructure must be configured separately. Readiness requires database and Redis connectivity; the API liveness endpoint does not. Audit export and distributed tracing remain to be implemented.

The patient workspace discards document, transcription, and note responses from earlier patient selections; patient-specific profile, consultation, and assistant panels reset on selection changes. Changing selection cannot cancel an action already accepted by the server, so clinicians must verify the patient before submitting. The doctor worklist supports name or exact-ID search and paginates up to 100 patients at a time, with independently paginated groups of up to 50 items in each category drawn only from the current patient page. It checks current account, relationship, and scope grants before release; selecting a result does not grant access to the underlying resource. A transcription appears as pending only when the latest processing job completed and its latest structured version remains unverified. Search is sent in the request body rather than the URL. The previous-view control re-fetches up to 100 earlier worklist views and checks access again; searching resets this navigation history. Background refresh and real-time notifications are not implemented. If a patient or item cursor is no longer authorized, refresh the search. Changes in patient names, consent, or review status while paging can change the results.

In-app notifications are durable database records, with a read marker and pages of up to 100; refresh returns to the newest page. Clinician notification visibility rechecks the active relationship and patient account; note-review notifications additionally require current clinical-note consent. The patient receives document processing outcomes and can open the exact referenced processing run; access is checked again and deleted documents are unavailable. Final processing writes serialize with account deactivation: a worker that obtains the account lock first may finish before deactivation; a worker that observes the deactivated account does not save extracted data. Relationship and consent changes notify the clinician without including user-entered purpose or clinical content. These are not external deliveries: there is no general email provider, outbox, retry policy, or push delivery. Each page checks current visibility; a cursor that is no longer accessible is rejected. Broker publication failures leave document jobs queued while the dispatcher retries; processing failures create a notification.

Rejection requires a clinician-entered reason, retained on the rejected version; older rejections may not have one. A doctor with current note consent can compare two versions using a line-based display limited to 1,000 lines per version. This highlights textual changes, not clinical meaning, and does not distinguish a final newline. Comparisons may include drafts and rejected content and are therefore unavailable to patients. Approved versions are preserved as superseded when a later version is approved.


Clinical note review policy is configured at API startup with `NOTE_REVIEW_POLICY=self_or_independent` (default) or `independent`. Independent review requires a different verified doctor with current clinical-note consent for both approval and rejection; the author is not notified as an eligible reviewer. If no other doctor has access, the note remains pending until an eligible doctor is authorized. Policy changes affect future reviews and do not retroactively invalidate earlier approvals. Restart all API instances together when changing the setting; inconsistent instance configuration can produce inconsistent enforcement. The synthetic seed script assumes the default self-review policy. This setting does not substitute for clinical governance.

Model-provider HTTP requests for chat and embeddings bypass environment-configured proxies and CA overrides (`trust_env=False`), do not follow redirects, and require uncompressed responses of at most 2 MB. Configure a directly reachable Ollama endpoint with a certificate trusted by the application environment; deployments needing a custom proxy or CA require an explicitly designed configuration. Provider limits and safety checks do not establish clinical reliability.

Knowledge approval defaults to `KNOWLEDGE_REVIEW_POLICY=self_or_independent`; set it to `independent` to require an administrator other than the source creator. The policy is enforced at approval and applies prospectively; existing approvals remain valid. Restart all API instances with the same configuration. This separation is administrative and does not establish independent clinical review or source authenticity.

A clinician creating a note can optionally link a completed processing run for the selected source document. The API checks patient ownership and document consent, and preserves the run ID across revisions and amendments unless the source is explicitly changed. Reprocessing leaves the link pointing to the earlier run; opening it rechecks document access. Revisions and amendments retain document references by default, but the clinician can explicitly remove them from the new version; previous versions retain their history. The clinician may also reference the saved transcription version and up to 30 specific fields, which remain identifiable if a later review changes the transcription. Field references store their group, item number and field name rather than copying extracted values. A clinician can optionally attach an exact quotation from the note to a field; it must occur once in that note. This is a clinician-declared link, not proof that the field supports the statement. Revisions retaining the source must preserve linked quotations exactly, or explicitly remove the document references. Unsaved review edits are not cited. The link does not verify the source or note. Document deletion removes extracted content even when a note retains its reference.

The patient document list returns up to 100 items per page, ordered by creation time and ID. The workspace can load older pages; document and extracted-record page requests each recheck access. Opening a cited or extracted result can retrieve its processing metadata even if that document is not on the currently loaded list page. Refreshing the workspace returns to the newest page.

Patients can view a paginated subset of successful clinician authorization checks and actions under Clinician access activity. It exposes a doctor ID, action and time, without document text, resource IDs or purpose. These entries are not proof that information was delivered or read, and the view is not a complete audit log: it excludes denied attempts, patient activity, administrative events and actions outside the selected list. Historical visibility also depends on the actor still being recorded as a doctor.

Administrators can assign a draft knowledge source to an active verified doctor for a recommendation or decline. The reviewer sees only assignments made to them, and decisions are recorded and audited; a decline requires a reason. Set `KNOWLEDGE_CLINICAL_REVIEW_POLICY=required` to require the most recently assigned doctor to recommend the source and remain active and verified before administrator approval. The default `optional` policy does not enforce clinical review. New assignments record the clinician verification revision and a SHA-256 fingerprint of the source text and publication metadata. A verification change invalidates the assignment even if the clinician is later re-verified; changes to source material likewise prevent a decision or required-review approval. Reviews created before fingerprinting or verification-revision binding remain visible but cannot satisfy the required gate; create a new source version and assignment. Each doctor can be assigned once per source version; a new review by the same doctor requires a new source version. Existing approved sources are not retroactively invalidated. The doctor screen shows up to 50 pending assignments and the admin screen up to 100 per source. Policy changes apply to future approvals only, and API instances must use the same configuration. These controls do not verify source authenticity, reviewer specialty, completeness, or clinical safety, and do not replace a clinical governance process.

## Synthetic summary evaluation

An opt-in Ragas evaluation compares generated document summaries with synthetic source text and hand-written reference summaries. Setup, limits, and instructions are in [evaluation/summaries/README.md](evaluation/summaries/README.md). The fixtures are illustrative and not clinician-reviewed; scores do not verify an individual summary or establish clinical safety.

New document summaries process extracted text in batches of up to three chunks. Each chunk is at most 2,000 UTF-8 bytes and splits only between lines; inputs are limited to 90 chunks and 180,000 bytes in total. Empty or missing extracted pages, longer individual lines, and larger inputs are rejected rather than silently omitted. Each batch and the final release recheck authorization. Summary-generation calls request a 16,384-token context and ask Ollama to reject truncation and context shifting; verify that the configured Ollama service honors those flags. Summarization has a 10-minute total timeout and may still fail on slow or unreliable models. Older saved summaries may have used partial text. All summaries remain unverified: sending complete extracted text does not establish factual correctness, and citations do not verify individual claims. Review the original with a clinician.

Document processing also provides a separate arithmetic comparison for saved structured laboratory rows with a test name, numerical result, and simple numerical reference interval or one-sided bound. Unsupported or ambiguous formats, overlapping result inequalities, inconsistent source locations, and conflicting reported flags return “unable to determine.” Comparisons use the transcribed values, do not validate units or source fidelity, and are not a diagnosis. The parser does not recognize arbitrary report tables; a clinician may need to transcribe and review the fields against the original. No conclusions are taken from AI summary text.

Native PDF table recognition requires a four-column header (test description, value, unit, reference range) and matching column geometry. Extracted rows may be wrong, duplicated, or omitted; comparisons use transcribed numbers and do not verify units. A reported high or low flag is shown separately, including where a multi-category range cannot be compared. Existing documents must be reprocessed to use the newer table parser.
